# 第 9 章：Runes —— 现代化的 OP_RETURN "回归"

## Runes —— 现代化的 OP_RETURN 回归

### 从 witness 复杂化到 OP_RETURN 简化

在第八章我们看到，Ordinals 和 Atomicals 将 witness 和 Taproot 的能力推向极致，
催生了 BRC-20 等代币协议，但也暴露了问题：

- 代币状态完全依赖链下索引器解析
- 不同索引器可能产生不同结果
- 与比特币原生 UTXO 模型脱节
- 需要复杂的索引基础设施

2024 年 4 月（比特币第四次减半时），Ordinals 创始人 Casey Rodarmor 推出了 **Runes** 协议，
选择了一条几乎"反高潮"的路径：

**不再滥用脚本，不再塞进复杂结构，而是回归简单的 OP_RETURN 模式。**

可以把它看作：

**Omni 的一个"现代化重构版"：**
- 结构更简单
- 只做 token
- 更容易解析
- 代币状态直接绑定 UTXO
- 无需复杂索引器

本章将解析：

- Runes 为什么是对 BRC-20 混乱的"修正"
- 它如何回归 OP_RETURN 路线
- UTXO 绑定机制如何工作
- 它在数据嵌入史中的象征意义

---

## 10.1 Runes 的背景：对 BRC-20 混乱的回应

### 10.1.1 BRC-20 的问题

BRC-20 使用 Ordinals 铭刻 JSON 来定义代币：

```json
{
  "p": "brc-20",
  "op": "deploy",
  "tick": "ordi",
  "max": "21000000",
  "lim": "1000"
}
```

**核心问题：**

1. **完全依赖链下索引器**：代币状态必须通过扫描所有铭刻交易来重建
2. **索引器分歧**：不同索引器可能产生不同的余额结果
3. **与 UTXO 脱节**：代币转账不遵循比特币的 UTXO 规则
4. **解析复杂**：需要解析 JSON、处理铭刻顺序、维护状态数据库

### 10.1.2 Runes 的设计哲学

Runes 的理念相比之前那些协议要极其克制：

- 不试图建全功能平台
- 不搞复杂合约
- 不做链上对象树
- **专注于在 OP_RETURN 里放一条简单指令：**
  "谁拥有多少某个 Rune。"

这与 Omni 的差异主要在：

- 设计更简化、字段更固定
- 对符号、命名、ID 进行统一规范
- **代币状态直接绑定 UTXO**（关键创新）
- 针对现代比特币生态做了兼容性考量
- 尝试减轻解析与实现负担

**换句话说：**

Runes 是对"OP_RETURN 当 token 协议"的现代化重写，而不是全新发明。
它吸取了 Omni 的"事件日志"模式，并引入了 UTXO 绑定机制。

---

## 10.2 Runes 的核心：UTXO 绑定的代币模型

### 10.2.1 UTXO 绑定机制

Runes 的关键创新是**将代币状态直接绑定到 UTXO**：

- 代币余额存储在特定的 UTXO 中
- 转账就是花费包含代币的 UTXO，创建新的 UTXO
- **概念上不再依赖一个全局、复杂的链下状态机，只需要按 UTXO 维度做索引**

**重要澄清：**

虽然 Runes 将余额绑定到 UTXO，但计算当前余额仍需要索引器扫描历史 runestones（OP_RETURN 中的消息），应用 edicts（分配指令）来重建状态。
Bitcoin Core 节点不原生支持 Runes 查询，必须使用索引器（如 ord）来处理序列化的 edicts。

**与 BRC-20 的区别在于：**

- Runes 的索引模型更贴近 UTXO，本身更简单
- 不需要维护复杂的事件重放状态机
- 不需要解析 JSON 和处理铭刻顺序
- 在给定同一版规则的前提下，所有实现对同一链数据的解析应当是一致的

这与 BRC-20 的根本区别：

| 维度 | BRC-20 | Runes |
|------|--------|-------|
| 状态存储 | 链下索引器维护全局状态 | **UTXO 中，但需索引器计算** |
| 转账逻辑 | 解析 JSON 指令 | **花费 UTXO + edicts** |
| 余额查询 | 扫描所有铭刻 JSON | **扫描 runestones，按 UTXO 索引** |
| 索引器 | 必需（复杂状态机） | **必需（但模型更简单）** |

### 10.2.2 为什么选择 OP_RETURN？

Runes 选择 OP_RETURN 而非 witness，原因包括：

1. **简单性**：OP_RETURN 是比特币最直接的数据入口
2. **可见性**：数据创建时永久可见，无需 commit-reveal
3. **UTXO 兼容**：OP_RETURN 输出虽然不可花费，但可以与其他输出组合
4. **政策稳定**：OP_RETURN 是比特币 Core 明确支持的数据通道（注：从 2025 年视角看，Bitcoin Core 的 OP_RETURN 政策已相对稳定，无重大变化）
5. **容量足够**：在当前的标准中，OP_RETURN 负载空间相对有限，但对 Runes 这类紧凑编码的指令来说已经足够

**与 witness 的对比：**

| 特性 | Witness (Ordinals/BRC-20) | OP_RETURN (Runes) |
|------|---------------------------|-------------------|
| 成本 | 1 WU/byte（75% 折扣） | 4 WU/byte |
| 可见性 | 需要 commit-reveal | 立即可见 |
| UTXO 绑定 | 困难 | **直接** |
| 解析复杂度 | 高（需要解析脚本） | 低（直接读取） |

## 10.3 Runes 的结构特征：短、小、定型、易解析

### 10.3.1 数据格式

一个 Rune 操作在链上的表现主要是：

```
OP_RETURN <payload>
```

协议里把这些 OP_RETURN 消息统一叫做 **Runestone**。

**Runestone 的三类消息：**

- **Etch（创建）**：创建新的 Rune 代币
- **Transfer（转账）**：通过 edicts 分配代币到输出 UTXO
- **Burn（销毁）**：销毁代币

payload 的结构（简化示意）：

| 字段 | 长度 | 含义 |
|------|------|------|
| 协议头 | 4 bytes | Rune 协议标记（ASCII 'R'） |
| 操作类型 | 变长 | Etch / Transfer / Burn |
| 资产标识 | 变长 | Rune ID 或名称（LEB128 编码） |
| Edicts | 变长 | 分配指令列表（rune ID、amount、output index） |
| 可选字段 | 变长 | 其他参数 |

**技术细节：**

Runestone 使用 LEB128 编码 varints（128-bit 整数序列）来压缩数据。
如果 payload 无效，会触发"cenotaph"机制（烧毁输入 runes）。
这个机制防止了无效交易滥用协议，增加了协议的鲁棒性：
无效的 runestone 不会导致代币丢失到未知地址，而是被明确销毁，避免了状态混乱。

**重点是：**

- 不使用脚本滥用
- 不引入多签数据载荷
- 不尝试将复杂状态全部编码进链上
- 把解析规则压缩到一个相对稳定、可预测的格式里

### 10.3.2 与 Omni 的格式对比

| 维度 | Omni | Runes |
|------|------|-------|
| 协议头 | 4 bytes ("omni") | 4 bytes (Rune 标记) |
| 版本号 | 2 bytes | 简化（可能省略） |
| 指令类型 | 2 bytes | 1-2 bytes |
| 字段设计 | 灵活但复杂 | **固定且简单** |
| 扩展性 | 支持多种资产类型 | **专注 token** |

## 10.4 与 Omni 的对比：从"万金油平台"到"专用简化协议"

### 10.4.1 设计目标对比

| 协议 | 设计目标 | 复杂度 | 表达范围 |
|------|---------|--------|---------|
| Omni | 通用资产层 + DEX | 高 | 广，但实现成本高 |
| Runes | 专注 token 协议 | 中低 | 窄但清晰 |

### 10.4.2 架构模式对比

**Omni 模式（事件日志）：**

```
链上：OP_RETURN 指令（事件日志）
链下：状态机扫描所有指令，重建当前状态
```

**Runes 模式（UTXO 绑定）：**

```
链上：OP_RETURN runestone（edicts） + UTXO 绑定
链下：索引器扫描 runestones，按 UTXO 维度建立索引（比 Omni 更简单）
```

### 10.4.3 在"嵌入数据"视角中的意义

Runes 意味着工程师开始反思：

**"我们真的需要一个所有东西都在链上的超级协议吗？"**

而是：

- 回到简单模型
- 将更多逻辑交给客户端
- **利用 UTXO 模型本身的状态能力**
- 保持 OP_RETURN 的简单、可审计性

## 10.5 Runes 与 BRC-20 的技术对比

### 10.5.1 状态管理对比

**BRC-20：**

```
1. 扫描所有 Ordinals 铭刻
2. 解析 JSON 指令
3. 维护链下状态数据库
4. 不同索引器可能产生不同结果
```

**Runes：**

```
1. 索引器扫描历史 runestones（OP_RETURN 消息）
2. 应用 edicts 计算每个 UTXO 的余额
3. 状态绑定到 UTXO，但需索引器计算
4. 在给定同一版规则的前提下，解析结果应当一致
```

### 10.5.2 转账流程对比

**BRC-20 转账：**

```
1. 创建新的铭刻（JSON 转账指令）
2. 索引器解析指令
3. 更新链下状态数据库
4. 钱包查询索引器获取余额
```

**Runes 转账：**

```
1. 花费包含代币的 UTXO
2. 在 OP_RETURN 中写入 runestone（包含 edicts）
3. Edicts 指定代币分配到哪些输出 UTXO
4. 索引器扫描 runestone，更新 UTXO 余额索引
5. 钱包查询索引器获取余额（或自己运行索引器）
```

### 10.5.3 钱包实现复杂度

| 维度 | BRC-20 | Runes |
|------|--------|-------|
| 必需组件 | 索引器 + 复杂状态数据库 | **索引器 + UTXO 索引** |
| 同步成本 | 扫描所有历史铭刻 JSON | **扫描历史 runestones，按 UTXO 索引** |
| 实现难度 | 高（JSON 解析、状态机） | **中低（固定格式、UTXO 模型）** |
| 依赖第三方 | 是（复杂索引器） | **是（但模型更简单，可自建）** |

## 10.6 在数据嵌入史中的位置：一次"回归"与"收束"

### 10.6.1 历史演进路径

```
彩色币（隐式状态）
  ↓
Omni（OP_RETURN 事件日志）
  ↓
Counterparty（OP_RETURN + 多签双通道）
  ↓
Stamps（裸多签极端化）
  ↓
P2WSH（witness 结构化容器）
  ↓
Ordinals/Atomicals（witness 数据爆炸）
  ↓
BRC-20（witness JSON 代币，索引器依赖）
  ↓
**Runes（回归 OP_RETURN，UTXO 绑定）**
```

### 10.6.2 Runes 的象征意义

Runes 标志着：

- 在 witness + Taproot 被大量用作内容/对象承载之后
- 社区出现了一股倾向：
- **把复杂度压回 off-chain，把链上 token 协议做得尽量简单**

从"非交易数据史"的视角看，它像是一个：

**"第一代 Omni 的现代重写版本"**

在经历彩色币 → Omni → Counterparty → Stamps → P2WSH → Ordinals → Atomicals 之后，
对 OP_RETURN 路线做的一次"减法设计"。

### 10.6.3 在数据嵌入史中的位置

| 时代 | 协议 | 数据位置 | 特点 | 状态管理 |
|------|------|---------|------|---------|
| 早期 | Omni | OP_RETURN | 事件日志 | 链下状态机 |
| 中期 | Counterparty | OP_RETURN + 多签 | 双通道 | 链下状态机 |
| SegWit | P2WSH | Witness | 结构化容器 | 链下解析 |
| Taproot | Ordinals/BRC-20 | Witness | 数据爆炸 | **链下索引器** |
| **现代** | **Runes** | **OP_RETURN** | **简化回归** | **UTXO 绑定** |

**关键洞察：**

Runes 不是技术的倒退，而是设计的成熟。
它证明了：**简单、可验证、与比特币原生模型一致的设计，比复杂的功能堆砌更有价值。**

---

## 10.7 小结：OP_RETURN 路线的现代化

Runes 展示了一个重要趋势：

**在经历了 witness 时代的复杂化之后，**
**工程师开始回归 OP_RETURN 的简单性，**
**并利用 UTXO 模型本身的能力。**

**工程意义：**

- OP_RETURN 仍然是比特币最直接、最简单的数据入口
- UTXO 绑定使得代币状态模型更贴近比特币原生模型，索引更简单
- 虽然仍需要索引器，但不再需要维护复杂的事件重放状态机
- 设计降低了实现门槛，提高了可验证性

**设计哲学：**

- 不是所有功能都需要在链上实现
- 利用比特币原生模型（UTXO）比创建新模型更可靠
- 可审计的设计比复杂的功能堆砌更适合长期演进

**在数据嵌入史中的位置：**

Runes 标志着 OP_RETURN 路线的现代化回归。
它不是对 witness 路线的否定，而是展示了：
**不同的数据嵌入方式适合不同的用例。**
**对于代币协议，简单、UTXO 原生的设计可能比复杂的 witness 结构更合适。**

下一章，我们将把视角真正拉到"链下状态机 + 链上承诺"的顶点——RGB。

RGB 代表了另一种设计哲学：
**最小化链上数据，最大化链下验证，**
**通过密码学承诺保证状态一致性。**
