# Chapter 6 Stamp / Stamps —— 裸多签作为"图片容器"

## Stamp / Stamps —— 裸多签作为"图片容器"

### 滥用脚本结构的极限实验

Stamps（广义上指 Stamp 协议及相关实践）是对 Counterparty 路线的一次极端化演绎：

既然可以在多签公钥里塞数据，那干脆把整个数据都塞进去。
我不再只放参数，而是把图像、内容本身编码为"公钥"。

这是一种完全"反脚本语义"的行为：

- 公钥不再代表一个可验证的椭圆曲线点
- 多签不再为了签名，而是为了滥用结构
- 脚本本身变成了一种"数据打包格式"

本章要做的是：

- 从结构上解释 Stamps 的具体做法
- 展示如何把 binary data 拆片塞进伪公钥
- 说明这种方式为什么在工程上极不友好
- 解释它为何仍然有"历史意义"与"研究价值"

---

## 6.1 Stamps 的目标：从状态机到纯数据可用层

回顾上一章：Counterparty 用裸多签塞数据，但它的目的是什么？

**Counterparty 的多签是为状态机服务的。**

- OP_RETURN 放指令头（操作类型、资产 ID）
- 多签放扩展参数（当 payload 超过 80 字节时）
- 数据的意义在于：**驱动链下状态机的状态转移**
- 理论上，这些 UTXO 可能被花费（虽然实际很少）

Stamps 做了什么？

**把 Counterparty 的"副产品"变成了"主业"。**

Counterparty 说：我用多签存参数，顺便把数据塞进去。
Stamps 说：我就是要存数据，多签只是容器，图片才是目的。

这是一个本质性的转变：

| | Counterparty | Stamps |
|---|-------------|--------|
| 核心目标 | 链上状态机（资产发行、转账） | 链上永久存储（图片、艺术品） |
| 数据角色 | 状态转移的参数 | 存储本身就是目的 |
| 多签用途 | 扩展 OP_RETURN 容量 | 唯一的数据入口 |
| 花费意图 | 理论上可能 | 明确不打算花费（Key Burn） |
| 设计哲学 | 金融协议 | 数据可用层 |

Stamps 的设计意图很明确：

**让数据"永远"存在于 UTXO 集中，不可被修剪。**

这就是"僵尸 UTXO"策略：

- 创建一个理论上可花费、但实际不可能花费的输出
- 节点必须保留它（因为不知道它是否会被花费）
- 数据就这样被"绑架"在 UTXO 集中，永远无法清理

从 Counterparty 到 Stamps，是从"协议设计者不得已的选择"到"故意利用系统资源"的转变。

## 6.2 工程核心：如何把数据编码成"伪公钥"

### 基本编码流程

1. **原始数据准备**（比如一张小图）
   - 压缩 / 重新编码（如果需要）
   - 转换为二进制数据

2. **数据分块**
   - 拆分成若干固定长度块，每块 31 字节
   - 最后一个块可以不足 31 字节（需要填充）

3. **伪公钥编码**
   - 对每块加上 `0x02` 或 `0x03` 前缀 → 变成 33 字节
   - 前缀选择：通常使用 `0x02`（表示 y 坐标为偶数）

4. **构造多签脚本**
   ```
   OP_1 <fake_pk_1> <fake_pk_2> ... <fake_pk_n> OP_N OP_CHECKMULTISIG
   ```

### 节点视角 vs 协议解析器视角

**节点视角：**

"这是一个合法的多签输出。"

**协议解析器视角：**

"这是这张图片或内容的第 N 片数据。"

每个多签输出可以承载若干个 31 字节片段，
多个输出可以拼接成完整 payload。

### 协议识别：解析器如何知道这是 Stamp？

Stamps 是一个独立协议，但使用了与 Counterparty 类似的多签数据编码技术。识别流程：

1. 扫描区块中的裸多签输出
2. 检查多签脚本格式（1-of-N multisig）
3. 提取所有公钥字段，检查是否符合 Stamp 编码模式
4. 如果符合，将伪公钥解码为数据块
5. 拼接数据块，验证是否为有效的图片/内容格式

Stamps 并没有发明新的链上结构，而是给裸多签数据赋予了特定语义：**将伪公钥字段直接解释为图片数据容器**。

## 6.3 Stamps 的数据恢复流程（解析视角）

解析器在扫描区块时的流程：

1. **发现特定格式的多签输出**（Stamp 约定的 pattern）
   - 识别裸多签脚本
   - 检查是否符合 Stamp 协议格式

2. **读取其中每一个 `<pubkey>`**
   - 提取所有公钥字段
   - 忽略脚本的其他部分

3. **数据提取**
   - 丢掉第一个字节（0x02/0x03），拿到 31 字节原始数据块
   - 去除填充（如果有）

4. **数据拼接**
   - 按预定顺序拼接所有数据块
   - 恢复原始数据流

5. **内容解释**
   - 将拼好的字节流解释为图片 / 文本 / 其他内容
   - 验证数据完整性

从工程角度看，这一过程与"从 P2WSH script 里还原数据"类似，
但它：

- 完全不关心签名
- 完全不关心椭圆曲线合法性
- 完全把 script 字段当作"随身硬盘"

### 真实交易案例分析

**Transaction:** `b1278acf50c27342753d01af9013a709509fdd920bc40ddcbec0738aaec2764c`

这是一个真实的 Stamp 交易。观察其输出地址：

```
bc1qapfywj2x8qukztqpcgqlxqqqqqqqqqrxqqq9zhp84vqqpq5t8lyqfvkk5y
bc1q5m4ywq8lcgq0hlxylh7axqqqqqqqqqqqqqqqqqqqqqqqqqqqqqsskk5xx9
```

**注意地址中大量重复的 "q" 字符**——在 bech32 编码中，`q` 代表 0。大量连续的 `q` 意味着原始数据中有大量零字节或重复模式，这是编码后图片数据的典型特征。

scriptPubKey 结构（简化）：

```
51                          # OP_1 (1-of-N)
21                          # PUSH 33 bytes
02[31 bytes of image data]  # 伪公钥 1
21                          # PUSH 33 bytes
02[31 bytes of image data]  # 伪公钥 2
...
53                          # OP_3 (N=3)
ae                          # OP_CHECKMULTISIG
```

关键点：**在 scriptPubKey 中，公钥只是被 push 到栈上，椭圆曲线合法性不会被验证。** 只有当有人尝试花费时，`OP_CHECKMULTISIG` 才会执行签名验证——但因为这些"公钥"没有对应私钥，没人会尝试，验证永远不会发生。

**Key Burn 机制**：Stamps 协议后来引入了 Key Burn，将多签中的一个公钥设为已知的 burn address（如 `0222...2222`），证明 UTXO 永远不可能被花费，让 Stamp 的"永久性"更加明确。

## 6.4 与 Counterparty 的对比：从"扩展数据"到"纯数据容器"

| 协议 | 多签用途 | OP_RETURN 用途 | 数据位置 |
|------|---------|--------------|---------|
| Counterparty | 扩展参数、结构化 payload | 指令头（type、property 等） | 双通道 |
| Stamps | 直接存储全部数据 | 可能仅做定位或元信息（可选） | 主要在多签 |

可以看出，Stamps 往前迈了一步：

**彻底将脚本数据空间"去金融化"，转而做纯粹的内容存储。**

从 Bitcoin Core 政策视角来看，这是非常危险的趋势——
如果大家都这么干，UTXO 集和 block data 都会迅速膨胀。

## 6.5 工程复现：Stamp 数据编码与解码

> **💡 完整代码实现：** 本节展示核心代码片段，完整可运行实现位于 `code/stamps/` 目录。

Stamp 的数据编码实现分为两个核心部分：数据分块编码和多签脚本构造。编码函数将原始数据按 31 字节分块，每块添加 `0x02` 前缀转换为 33 字节的伪压缩公钥；然后将伪公钥分组，构造 1-of-N 裸多签脚本。解码函数则从多签脚本中提取所有公钥字段，去除前缀后拼接还原原始数据。

解析器需要扫描区块中的裸多签输出，识别符合 Stamp 格式的脚本，提取伪公钥字段并解码为数据块，按顺序拼接恢复完整的图片或内容。这种设计使得 Stamp 能够将任意二进制数据嵌入到 UTXO 集的 scriptPubKey 中，但代价是永久占用 UTXO 集空间。完整实现包含错误处理、边界检查和数据完整性验证，详见 `code/stamps/` 目录。

## 6.6 Stamps 的问题：为何被视为"极端 spam"？

### 6.6.1 从 Core 视角

- 这些多签 UTXO 在理论上是可花费的
- 但实际上没人会去花费（私钥并不存在）
- 导致 UTXO 集污染（永远的"僵尸 UTXO"）
- 节点存储和同步负担被迫承担垃圾

**Policy 层面的反应：**

- **Bitcoin Core 0.13.0（2016年8月）**：引入 `-permitbaremultisig` 选项，用户可选择拒绝中继裸多签交易（默认仍允许）
- **Bitcoin Core 0.17.0（2018年10月）**：裸多签输出不再被钱包自动视为 "IsMine"，即使所有私钥都在钱包中

### 6.6.2 从协议工程视角

- 这种用法没有任何脚本语义价值
- 难以与标准多签交易区分（需要解析器 heuristics）
- 很难通过 policy 维持"数据/非数据"区分
- 使得脚本字段"语义退化"为纯字节数组
- 解析器必须扫描所有多签输出，判断是否为 Stamp

### 6.6.3 资源消耗问题

```python
# 示例：存储一张 100KB 的图片

image_size = 100 * 1024  # 100 KB
bytes_per_chunk = 31
chunks_needed = (image_size + bytes_per_chunk - 1) // bytes_per_chunk
outputs_needed = (chunks_needed + 19) // 20  # 假设每输出 20 个公钥

print(f"需要 {outputs_needed} 个多签输出")
print(f"每个输出占用 UTXO 集空间")
print(f"总计: {outputs_needed} 个永久 UTXO")

# 如果 BTC = $40,000，每个输出至少 600 satoshis
cost = outputs_needed * 600 / 100000000 * 40000
print(f"成本: ${cost:.2f}")
```

因此：

**Stamps 成为 mempool policy 与"比特币该不该当图床"的争议焦点之一。**

### 6.6.4 OLGA：Stamps 的进化

2024 年 2 月（区块高度 833,000），Stamps 协议引入了 **OLGA**（Optimized Lightweight Graphical Asset）格式：

| 特性 | 经典 Stamp | OLGA |
|------|-----------|------|
| 脚本类型 | 裸多签 (P2MS) | P2WSH |
| 编码 | Base64 | 原始二进制 |
| 交易大小 | 100% | ~50% |
| 成本 | 100% | ~30-40% |
| 最大容量 | ~7-8 KB | ~65 KB |

OLGA 的出现标志着 Stamps 协议的"自我修正"：承认了 witness 路线的成本优势，同时保持核心理念。

## 6.7 Stamps 的意义：极端点上的"边界标记"

虽然从工程和资源利用角度，它是一种不受欢迎的做法，
但从"非交易数据史"的视角看，它标记了一个关键边界：

**如果不给出清晰边界，任何脚本字段最终都可能沦为数据仓库。**

### Stamps 的历史意义

1. **标记了多签路线的极端点**
   - 将 Counterparty 的思路推向极致
   - 证明了"脚本即存储"的可行性（虽然不推荐）

2. **强迫社区正面讨论"什么是资源滥用"**
   - 引发了关于 UTXO 集管理的讨论
   - 推动了 policy 层的改进

3. **为 witness / Taproot 被接受为更合理的数据入口铺路**
   - 展示了脚本字段作为数据容器的局限性
   - 证明了需要更好的数据嵌入机制

### 后续演进

Stamps 是多签路线的极端点，
后续会逐渐被：

- **P2WSH / witness 嵌入**（数据在 witness，享受 75% 折扣）
- **Taproot Merkle 路线**（结构化、可验证）
- **客户端验证（RGB）**（链下状态 + 链上承诺）

所替代。

## 6.8 Stamp 在本书中的位置：脚本滥用的极端点

如果说：

那么 **Stamp** 就是：

**脚本结构滥用的极端点。**

### 在数据嵌入史中的位置

| 协议 | 数据入口 | 特点 | 问题 |
|------|---------|------|------|

### 它的重要性在于

- 强迫社区正面讨论"什么是资源滥用"

- 为 witness / Taproot 被接受为更合理的数据入口铺路
- 证明了需要更好的数据嵌入机制
