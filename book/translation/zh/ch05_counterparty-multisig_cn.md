# Chapter 5 Counterparty —— 裸多签数据容器的首次系统化实践

## Counterparty —— 裸多签数据容器的首次系统化实践

### 为什么是 Counterparty？

在 Omni 之后，比特币上出现了多个尝试扩展数据容量的协议。其中 Counterparty（2014年1月启动）是**第一个系统性、大规模使用裸多签作为数据容器的协议**。

虽然在它之前可能有零星的实验，但 Counterparty 将这一技术标准化、工程化，并在实践中大规模应用。它的多签数据编码方案后来直接启发了 Stamp 协议，成为"裸多签即存储"这条技术路线的开山之作。

更重要的是，它在 2014-2016 年间拥有真实的用户量和链上数据：
- 发行资产数量超过 50,000+
- 支撑了 Rare Pepes（2016）等早期 NFT 项目
- 运行着去中心化交易所（DEX）
- 是以太坊之前最完整的"链上资产协议"

本章聚焦 Counterparty 的核心技术贡献：**如何将数据编码进多签公钥位**，以及这一技术的优势与代价。

---

## 5.1 设计目标：不仅是资产，还要有"协议栈"

### 从"显式数据"走向"结构化载荷"

在 Omni 之后，人们已经接受一个事实：

**在比特币上实现资产与协议，必须显式写入数据。**

但 Omni 主要依赖单一通道：OP_RETURN。
它的载荷有限（80 bytes）、结构简单，对复杂状态机的表达能力不足。

Counterparty 则走得更远——它在工程上作了两个大胆尝试：

1. 继续使用 OP_RETURN 写协议指令
2. **利用多签公钥字段（裸多签）塞进更多结构化数据**

它因此成为：

- **裸多签数据容器的开创者与标准制定者**
- Stamp 协议的直接先祖
- 后续 Ordinals / Atomicals "数据塞进非预期字段"的启发源
- 多通道数据嵌入的第一个成熟范本

### Counterparty 的野心

Counterparty 的野心不止于"发个代币"，而是：

- 发行资产（Token）
- 实现去中心化交易（DEX）
- 支持可编程指令（bets、contracts 等）
- 尽可能不修改比特币共识

用本书的话说：

Omni 把"状态机"搬到了 off-chain，
Counterparty 则试图在链上承载更丰富的"指令语言"。

为此，它需要两个东西：

1. 一条干净的指令通道（OP_RETURN）
2. 一条容量更大的载荷通道（multisig 公钥位）

---

## 5.2 OP_RETURN 通道：指令头 + 协议识别

和 Omni 类似，Counterparty 使用：

```
OP_RETURN <payload>
```

payload 里包含：

- 协议识别（magic：`CNTRPRTY`）
- 指令类型（type：创建、转账、挂单……）
- 资产 ID 或 issuance 信息
- 金额 / 数量字段
- 部分附加参数

这个部分主要承担：

**"这里有一条 Counterparty 协议消息，它属于哪种类型？"**

但 Counterparty 很快就遇到问题：

**OP_RETURN 的字节数不够。**

为了承载更复杂的数据结构，它需要找到第二个出口。

---

## 5.3 裸多签通道：把数据当成"伪公钥"塞进去

### 多签脚本的结构

多签脚本形态：

```
OP_1 <pubkey1> <pubkey2> ... <pubkeyN> OP_N OP_CHECKMULTISIG
```

每个压入栈的 `<pubkey>` 在共识层仅需满足：

- 是一个 33 字节（压缩公钥）或 65 字节（未压缩公钥）的字符串
- 椭圆曲线点合法性验证只在有限程度上检查

于是 Counterparty 做出一个非常关键的工程决策：

**把任意数据编码为"伪公钥"，塞进多签脚本的公钥位置。**

### 伪公钥编码原理

**压缩公钥格式（33 bytes）：**

```
0x02/0x03 + 32 bytes 数据
```

- `0x02` 或 `0x03` 是压缩公钥的前缀（表示 y 坐标的奇偶性）
- 后 32 bytes 可以是任意数据

**未压缩公钥格式（65 bytes）：**

```
0x04 + 64 bytes 数据
```

- `0x04` 表示未压缩公钥
- 后 64 bytes 可以是任意数据

### 为什么伪公钥可行：共识验证行为

一个使这一技术成为可能的关键细节：

**比特币共识不会检查被压入栈的"公钥"是否是有效的椭圆曲线点，除非它参与签名验证。**

当公钥在脚本中被压入栈时，比特币的共识规则只验证：
- 字节长度（压缩公钥 33 字节，未压缩公钥 65 字节）
- 格式前缀（0x02/0x03/0x04）

完整的椭圆曲线点验证只在签名验证操作（OP_CHECKSIG、OP_CHECKMULTISIG 等）时进行，即公钥实际用于验证签名时。

Counterparty 正是利用了这一点：由于多签输出中的伪公钥永远不会用于签名验证（只有真实公钥用于此目的），它们可以是带有有效前缀的任意 32 字节载荷。脚本在共识层仍然有效，数据得以嵌入。

### Counterparty 的典型实现

Counterparty 使用 **1-of-3 multisig**：

```
OP_1 <fake_pubkey1> <fake_pubkey2> <real_pubkey> OP_3 OP_CHECKMULTISIG
```

- **前 2 个公钥**：伪公钥，编码数据
- **第 3 个公钥**：真实公钥，用于 reclaim BTC

这样的输出对 Bitcoin Core 来说，只是：

**这是一个合法的多签输出**

但对 Counterparty 解析器来说：

**这是存储协议载荷的容器（data carrier）**

它以此扩展了协议的可表达范围：

- 更大容量（每个公钥 33 bytes，2个公钥 = 64 bytes）
- 可以拆分到多个公钥位
- 支持复杂参数与结构化 payload

## 5.4 双通道协作：指令头 + 载荷体

典型模式：

- **OP_RETURN** 负责"这是什么指令"（指令类型、基本参数）
- **多签公钥位** 负责"这条指令的完整参数/数据"（扩展数据）

形象地说：

- OP_RETURN 是 HTTP 头
- 多签 payload 是 HTTP Body

### 解析流程

在解析时，Counterparty 客户端会：

1. 扫描交易中的 OP_RETURN，确认这是 Counterparty 消息
2. 再去解析同一交易中的多签输出，将公钥字段解码为数据
3. 组合成一条完整的协议指令
4. 更新链下状态机（谁拥有多少资产，谁挂了什么单）

### 示例：资产发行交易结构

```
交易结构：
  output[0]: OP_RETURN <counterparty-header>
    - magic: "CNTRPRTY"
    - type: "issuance"
    - asset_name: "MYTOKEN"
  
  output[1]: OP_1 <fake_pubkey1> <fake_pubkey2> <real_pubkey> OP_3 OP_CHECKMULTISIG
    - fake_pubkey1: 0x02 + 32 bytes (资产描述数据)
    - fake_pubkey2: 0x02 + 32 bytes (元数据扩展)
    - real_pubkey: 真实公钥，用于 reclaim dust
```

解析器组合后得到完整的资产发行指令。

### 通道对比：OP_RETURN vs 裸多签

Counterparty 的双通道方法利用了两种根本不同的数据嵌入机制。下表对比了它们的特征：

| 通道 | 容量 | 占用 UTXO？ | 可花费性 | 政策风险 | 攻击面 |
|------|------|------------|---------|---------|--------|
| OP_RETURN | 80 bytes | 否 | 无 | 低 | 最小 |
| 裸多签 | 33×N bytes | 是 | 困难 | 高 | 格式错误脚本、UTXO 膨胀 |

**关键差异：**

- **OP_RETURN**：可证明不可花费，不污染 UTXO 集，但限制为 80 字节。Bitcoin Core 政策明确支持其作为数据通道。
- **裸多签**：容量更高（每个公钥 33 字节，可扩展），但永久占用 UTXO 集，难以花费，且面临日益增加的政策限制。

Counterparty 的创新在于结合两者：使用 OP_RETURN 进行协议识别和基本参数，同时利用裸多签承载扩展载荷。这种混合方法在最大化容量的同时，保持了一定程度的政策接受度。

## 5.5 核心编码原理总结

Counterparty 的裸多签数据编码可以总结为三个核心步骤：

### 步骤 1：数据分块

将待编码的数据按 32 bytes 分块：

```
原始数据：[200 bytes]
分块后：
  - chunk1: 32 bytes
  - chunk2: 32 bytes
  - chunk3: 32 bytes
  - ...
```

### 步骤 2：编码为伪公钥

每个数据块添加公钥前缀：

```
chunk1 → 0x02 + chunk1 = fake_pubkey1 (33 bytes)
chunk2 → 0x02 + chunk2 = fake_pubkey2 (33 bytes)
...
```

### 步骤 3：构造多签脚本

将伪公钥与真实公钥组合成多签脚本：

```
OP_1 
  <fake_pubkey1> 
  <fake_pubkey2> 
  <real_pubkey>
OP_3 
OP_CHECKMULTISIG
```

这样，Counterparty 就实现了：

- **共识层**：这是一个合法的 1-of-3 多签输出
- **协议层**：这是一个包含 64 bytes 数据的容器

## 5.6 工程复现：双通道数据嵌入

> **💡 完整代码实现：** 本节展示核心代码片段，完整可运行实现位于 `code/counterparty/` 目录。

Counterparty 的双通道数据嵌入实现分为两个核心部分：伪公钥编码/解码和交易构造/解析。编码函数将任意 32 bytes 数据添加 `0x02` 前缀转换为 33 bytes 的伪压缩公钥；解码函数则反向提取原始数据。交易构造时，OP_RETURN 输出承载协议指令头，多签输出承载扩展数据载荷，两者组合形成完整的协议消息。

解析器需要同时扫描 OP_RETURN 和多签输出，将公钥字段解码后与 OP_RETURN 数据拼接，还原完整的协议指令。这种双通道设计使得 Counterparty 能够突破 OP_RETURN 的 80 bytes 限制，支持更复杂的资产发行、DEX 订单等场景。完整实现包含错误处理、边界检查和类型验证，详见 `code/counterparty/` 目录。

## 5.7 Counterparty 的兴衰：从辉煌到边缘化

### 5.7.1 巅峰期（2014-2016）

Counterparty 在早期取得了显著成功：

**技术成就：**
- 2014年1月启动，通过 Proof-of-Burn 销毁 2,140 BTC 分发 XCP
- 首次在比特币上实现完整的 DEX + 资产发行 + 智能合约
- 2014年7月：Overstock.com 的 tZERO 项目选择 Counterparty
- 2015年：Spells of Genesis（首个链上游戏资产）
- 2016年：Rare Pepes（NFT 概念的先驱，早于 CryptoPunks 1年）

**链上数据：**
- 累计发行资产：50,000+
- 高峰期日交易量：数千笔
- 是 2014-2016 年比特币上最活跃的元协议

### 5.7.2 衰落的原因（2017+）

**1. 以太坊的崛起（2017-2018）**
- ERC-20 标准更简单、更灵活
- Gas 模型比比特币手续费更可预测
- 智能合约功能更强大
- 开发者生态迅速转向以太坊

**2. Bitcoin Policy 的限制（2016+）**
- Bitcoin Core 0.13.0（2016）引入 `-permitbaremultisig` 选项
- 节点可以选择拒绝裸多签交易
- 现代 policy 只接受最多 3-of-N 的 multisig
- 对 Counterparty 的多签数据容器构成直接限制

**3. 高昂的比特币手续费（2017 牛市）**
- 2017年底比特币手续费飙升至 $50+/tx
- Counterparty 交易需要多个输出，成本更高
- 用户转向更便宜的链

**4. 缺乏 Killer App**
- Omni 有 USDT（真正的产品市场契合）
- Counterparty 的艺术品/收藏品市场太小众
- Rare Pepes 虽然有历史意义，但商业价值有限

### 5.7.3 今天的状态

- 协议仍在运行，但活跃度大幅下降
- 转向 P2TR 等现代编码方式（已废弃裸多签）
- 主要价值：历史意义 + NFT 收藏品市场

## 5.8 优点与代价：Counterparty 暴露的结构性问题

### 优点

- 利用现有结构（多签公钥位）扩展容量
- 不需要新 opcode
- 不改变共识
- 协议可迭代
- 表达力显著强于纯 OP_RETURN

### 代价

#### 1. 裸多签 = policy 层不喜欢的模式

- 占用 UTXO
- 难以花费（理论上需要多个签名，虽然 Counterparty 用 1-of-N 规避）
- 混淆了脚本语义（明明是数据，却伪装成密钥）
- Bitcoin Core 0.13.0+（2016）引入限制，节点可选择拒绝裸多签
- 现代 policy 只接受最多 3-of-N 的 multisig

#### 2. Block/UTXO 资源被当成数据存储

- 对节点负担较大
- 与 "UTXO should be minimal" 的理念冲突
- 永久占用 UTXO 集空间（虽然可以 reclaim，但实践中很多未 reclaim）

#### 3. 解析器复杂度上升

- 必须同时解析 OP_RETURN 和 multisig
- 必须防御错误格式、攻击载荷、恶意脚本
- 需要处理多签脚本的各种变体

#### 4. 为后续"滥用脚本作为存储"树立了先例

- Stamp、部分 Ordinals 风格的尝试，直接继承了这条路
- 开启了"脚本即存储"的设计范式

## 5.9 Counterparty 在本书中的位置：多通道嵌入与脚本结构的第一次滥用

如果说：

- **彩色币** 是零字节协议
- **Omni** 是单通道显式数据协议

那么 **Counterparty** 就是：

**双通道嵌入 + 结构化载荷协议。**

### 它的意义有三层：

1. **证明 OP_RETURN 不够用，协议会主动寻找第二出口**
   - 当单通道容量不足时，协议设计者会寻找其他数据入口
   - 这为后续 witness、Taproot 的使用奠定了基础

2. **打开"多签字段可作为数据容器"的潘多拉魔盒**
   - 首次系统性地将脚本字段用作数据存储
   - 证明了"共识允许但语义滥用"的可行性

3. **为后续 Stamps、裸多签、脚本隐藏数据奠定实践基础**
   - Stamp 协议直接继承了 Counterparty 的多签数据容器思路
   - Ordinals 和 Atomicals 也受到这种"非预期字段利用"的启发

### 在数据嵌入史中的位置

| 协议 | 数据入口 | 特点 |
|------|---------|------|
| 彩色币 | 无（零字节） | 纯解释层 |
| Omni | OP_RETURN | 单通道，80 bytes |
| **Counterparty** | **OP_RETURN + 裸多签** | **双通道，结构化** |
| Stamp | 裸多签 | 单通道，极端化 |
| Ordinals | Witness | 单通道，大容量 |
| Atomicals | Witness + Taproot | 多通道，结构化 |

## 5.10 小结：Counterparty 的工程意义

Counterparty 代表：

- ✔ 多通道数据嵌入的第一个成熟范本
- ✔ 脚本结构"语义滥用"的首次系统性实践
- ✔ 证明了协议设计者会主动寻找数据入口
- ✔ 为后续协议（Stamp、Ordinals）提供了技术路径
- ✔ 暴露了裸多签作为数据容器的优缺点

并为后续发展指明方向：

**当单通道不够用时，协议会寻找第二、第三通道。**
**但每个通道都有其代价和限制。**

这就引出了下一章：

**第 6 章：Stamp —— 裸多签的极端化**

Stamp 将 Counterparty 的多签数据容器思路推向极端，完全依赖裸多签，成为"多签即存储"的典型代表。
